### 发现的缺陷

首次连接成功后执行任何一条 shell 命令即失败，界面报 `ADB 连接失败：java.io.IOException: Stream closed.`，会话被判定为断开；点「开始投屏」也会在读取显示尺寸的 `wm size` 上以同样错误中断。

根因在第三方库 libadb-android 3.1.1：`AdbStream.read()` 在对端已发 CLSE、且最后一批负载已被读空的情况下抛出 `IOException("Stream closed.")`，而不是像 `InputStream.read()` 约定的那样返回 EOF；`AdbInputStream` 只在进入读取前检查 `isClosed()`，因此是否抛错取决于 CLSE 与最后一次读取的先后顺序，属于竞态。应用把该异常当成致命错误，`AdbSession.shell()` 随即调用 `fail()` 拆掉整个 ADB 会话。

修复：新增 `AdbPeerInputStream`（纯 Java，可 JVM 单测），把 libadb 的 `Stream closed` 异常翻译为 EOF，同时保留原有的有符号字节修正；`LibAdbTransport` 改为使用该包装。该修复对命令、sync、控制流和视频流四条读取路径同时生效。

## 平板→车机 USB OTG 直连验收（2026-10-27 晚，数据线从电脑换接平板）

车机 USB 调试口接到平板的 OTG 口后，系统弹出「允许"车机投屏"访问 SA_LEMANS_IVI- 吗？」，点击「确定」后进入「等待系统 USB 授权」→「已连接」。

首次测试可在 USB 上连接并执行 shell 命令，但点「开始投屏」必失败：scrcpy server 上传卡住 10 秒后 `USB ADB timed out`。加报文级日志定位到两个缺陷：

1. **USB 批量传输长度恰好是 512 字节整数倍时对端收不到「传输结束」**。`1024`（2×512）和 `4096`（8×512）字节的数据包全部卡死，`48`/`92` 字节这类不整除的包正常。改为每包 `1000` 字节（非 512 倍数，末尾有短包）后上传立即通过，732,226 字节的 server 共发出 910 个包、无错误。
2. **sync 协议头逐字节写出**。`AdbSession.push` 原用 `DataOutputStream.writeBytes/writeInt`，每个字节触发一次 USB 往返（一次上传里出现十余个 `len=1` 的 WRTE）。改为一次写出 8 字节头。

修复后实测：

| 项目 | 结果 | 证据 |
| --- | --- | --- |
| 系统 USB 授权 | 通过 | 弹窗点「确定」后 `permission granted=true usable=true` |
| USB ADB 握手 | 通过 | `CNXN`→车机返回 `CNXN` 与 347 字节 banner，`maxPayload=4096`；车机 `ro.adb.secure=0`，无需 RSA 授权 |
| shell 命令 | 通过 | 健康检查与 `wm size` 均在 USB 链路上完成 |
| scrcpy server 上传 | 通过 | 910 个 WRTE 包无超时，车机启动 `com.genymobile.scrcpy.Server 4.0`，编码器 `c2.qti.avc.encoder` |

**每次重新连接都需要重新点「确定」**：断开或退出投屏后，车机 USB 会重新枚举（`/dev/bus/usb/001/0NN` 路径递增），Android 会清除该设备的 USB 授权，因此下次连接仍会弹授权框。
